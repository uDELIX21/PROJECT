**Course:** INFT 255 — System Analysis & Design
**Review status:** Candidate selection and structural/content desk review complete; awaiting approval before assessment-engine implementation.
**Authority note:** No lecturer answer key, official rubric, or past paper was supplied. Every selected answer explanation and marking guide is author-created, source-mapped, and **not lecturer-approved**.

---

## 1. Review purpose and evidence boundary

Modules 1–7 produced a source-mapped draft seed of 124 MCQs and 28 subjective prompts. A numeric draft total is not by itself a responsible assessment bank: overlapping revision prompts can create repetition, and app delivery needs a stable identifier set, verified explanation/source fields, and clear topic/cognitive metadata.

This review selects a canonical, non-repetitive **100-MCQ / 20-subjective** bank for the first functional assessment engine. It retains the remaining 24 MCQs and eight subjective prompts as documented **reserve/revision candidates**. Reserve status is not a claim that an item is wrong; it means it is not included in the initial scored canonical bank because it substantially overlaps selected coverage or is best reserved for a later adaptive revision form.

### Review method actually used

1. Re-read each module’s authored question table and subjective headings/model guides against the module source label and learning outcome.
2. Confirm every draft item has a stable ID, cognitive label, prompt, author-created correct-answer explanation/guide, and source locator in its module content package.
3. Select broad syllabus coverage, all five cognitive operations, calculation/model reasoning, and integrated cross-model evaluation—not a definition-only pool.
4. Mark near-duplicate revision prompts as reserve rather than silently using them to inflate the count.
5. Preserve source/assumption limitations. This is a desk/content review; it is not lecturer moderation, psychometric validation, or evidence that an official marking scheme exists.

## 5. Item-delivery metadata required for implementation

Each canonical MCQ must be represented locally in the final HTML data model with:

- stable `id`, module/topic, outcome, source locator, cognitive operation, prompt, choices, correct choice key, answer rationale, misconception/review pointer, and `canonical: true` status;
- an author-created/non-official assessment label;
- no live network requirement for question/feedback display;
- attempt/result fields separated from immutable question data.

Each canonical subjective item must add:

- prompt, module/topic, marks, model-answer HTML/text, marking-guide criteria, common-error/review pointer, source locator, and `canonical: true` status;
- a learner response field stored locally only after the learner enters text;
- a model-guide `revealed` state that is false by default and changes only after an explicit learner action.

### Assessment-session requirements for the next implementation step

1. **Topic practice:** learner chooses one topic; engine draws a balanced set from that topic and gives explanation feedback after each submitted answer.
2. **Mixed untimed practice:** engine draws a balanced set across completed/selected topics; learner can review before submit and receives outcome-specific recommendations.
3. **Timed exam simulation:** learner sees authored duration/section count, timer, review flags, explicit submit, local recovery state, and non-official result wording. No page open/click awards credit.
4. **Subjective practice:** learner writes first; model answer and marking guide remain hidden until `Reveal` is selected; reveal does not create mastery credit.
5. **Scoring/mastery foundation:** only submitted answers and correct/repaired learning activity outcomes may later update topic evidence; a question’s explanation/reveal alone is not evidence.

## 6. Final pre-implementation limitations

- The selected 100/20 bank is source-mapped and author-reviewed, but there is no lecturer key/rubric or psychometric/difficulty trial. It must remain explicitly non-official.
- Existing tables contain authored prompts/model guides in module documents, but they are not yet normalised into app data or independently browser-tested.
- Phase 6 must implement only approved canonical items first. Reserve items must not be quietly blended into scored sessions.
- The question count meets the target, but assessment quality also requires readable rendering, keyboard operation, answer/result persistence, boundary-case testing, accessibility review, and academic QA before final completion.
